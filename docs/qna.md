# 질문 & 답변 로그

프로젝트를 진행하며 나온 질문을 한 문장씩 기록한다. (최신이 아래)

## 2026-07-16

- **Q. TX15 Max의 student/teacher 기능으로 PC에서 ELRS→Betaflight까지 관제하려면 어떻게 구성하나?**
  → PC(Python) → Pro Micro(시리얼→PPM 변환) → DSC 트레이너 포트 → EdgeTX Trainer 믹싱 → 내장 ELRS → Betaflight 순의 체인으로 구성한다.

- **Q. 구입한 Pro Micro가 5V인지 3.3V인지 보드에 둘 다 적혀 있는데 어떻게 구분하나?**
  → 클론 보드는 공용 기판이라 둘 다 인쇄되어 있으므로, 1초 깜빡임 테스트(또는 크리스탈 각인, 멀티미터)로 판별해야 한다.

- **Q. 클럭 확인은 어떻게 하나?**
  → 16MHz 설정으로 컴파일한 스케치가 정확히 1초 간격으로 동작하면 16MHz 보드이며, 실측 결과 0.998~1.001초로 5V/16MHz 확정됐다.

## 2026-07-17

- **Q. 점퍼선을 꽂는 핀의 위치가 다이어그램과 달라도 되나?**
  → 다이어그램 위치는 개념도일 뿐이고 보드에 인쇄된 글자(10, GND)를 보고 꽂으면 되며, GND는 3개 중 아무거나 써도 된다.

- **Q. 3.5mm 나사조임식 플러그에 L/R 화살표가 있는데 어디에 연결하나?**
  → L = 팁(신호선, 10번 핀), 접지 표기 단자 = 슬리브(GND)이고 R(링)은 비워둔다.

- **Q. 점퍼선 색깔이 달라도 되나?**
  → 색은 사람이 구분하기 위한 관례일 뿐이며 어느 핀에서 어느 단자로 이어지는지만 맞으면 된다.

- **Q. EdgeTX TRAINER 화면의 Ail 0, Ele 6, Thr 582, Rud -2는 무슨 뜻인가?**
  → 학생(PC)이 보낸 Roll/Pitch/Throttle/Yaw 입력값으로, 범위는 약 -512(끝)~0(중앙)~+512(반대 끝)이며 잔값은 Calibration으로 0에 맞춘다.

- **Q. 왜 이름이 Ail/Ele/Thr/Rud인가?**
  → RC 조종기가 비행기에서 출발해 조종면 이름(Aileron/Elevator/Throttle/Rudder)을 그대로 쓰며, 드론에서는 각각 Roll/Pitch/모터출력/Yaw에 해당한다.

- **Q. .gitignore가 필요할까?**
  → 파이썬이 자동 생성하는 `__pycache__` 캐시 같은 파일이 커밋에 섞이는 것을 막기 위해 필요하다.

- **Q. 하드웨어 없이(리모트로) 작업할 수 있는 게 있나?**
  → 프로토콜 단위 테스트, 자동 제어용 안전 필터(SafetyLimiter), GitHub Actions CI(클라우드 빌드/테스트)는 하드웨어 없이 진행 가능하다.

## 2026-07-18 (하드웨어 디버깅)

- **Q. "Trainer signal lost/recovered"가 반복되는 건 왜인가?**
  → 신호가 순간순간 끊긴다는 뜻으로, 대부분 점퍼선·나사단자·플러그의 접촉 불량이 원인이며(실제로 선 교체로 해결됨), EdgeTX 이슈로 보고된 다른 원인으로는 PPM 극성 불일치와 내장 ELRS RF 간섭이 있다.

- **Q. PPM 신호가 너무 빠른 것 아닌가?**
  → PPM 프레임은 22.5ms(초당 약 44회)로 일반 조종기 스틱과 동일한 표준 규격이며, 화면 숫자가 빠르게 움직인 건 테스트 패턴의 속도일 뿐이다.

- **Q. 펄스 극성 LOW와 HIGH의 차이는?**
  → 정보(펄스 간 시간 간격)는 동일하고 펄스가 아래로 꺼지느냐(LOW, 평소 5V — EdgeTX 트레이너 기본 규격) 위로 솟느냐(HIGH, 평소 0V)의 차이로, EdgeTX 기본에 맞춰 LOW로 변경했다.

- **Q. 이 구성이 조종기 내부 부품에 손상을 줄 수 있나?**
  → DSC 포트는 외부 PPM을 받도록 설계된 입력이라 안전하며, 주의할 것은 헤드폰 잭(출력 단자)에 잘못 꽂지 않는 것과 보험용 1kΩ 직렬 저항 정도다.

- **Q. 왜 알루미늄 스틱을 만지고 있으면 신호가 제대로 들어오나?**
  → 전기 신호는 신호선(가는 길)과 GND(돌아오는 길)의 왕복 회로가 필요한데, GND가 끊겨 있어서 금속 스틱을 잡는 동안 사람 몸이 임시 "돌아오는 길" 역할을 했던 것이다 (전형적인 접지 단선 증상).

- **Q. GND를 ⏚ 단자가 아닌 R 단자에 두어도 괜찮은가?**
  → 단자 라벨은 잉크일 뿐이고 실제로 조종기 접지 접점과 이어지는 단자가 정답이므로 괜찮다 — 이 플러그는 ⏚ 단자가 내부 미연결(오표기/불량)이었고 R이 진짜 접지였다. 단, 플러그를 교체하면 매핑을 다시 확인할 것.

- **Q. 트레이너 모드에서 나는 선생(Teacher)인가 학생(Student)인가?**
  → 사용자(TX15 Max, Master/Jack)가 전파를 송신하고 최종 권한을 가진 선생이고, PC(Pro Micro 경유)가 케이블로 입력만 보내는 학생이며, SH 당김=조종권 위임, SH 놓음=즉시 회수다.

- **Q. Gazebo에서 Betaflight 기준으로 돌려서 sim-to-real gap을 줄일 수 있나?**
  → Betaflight SITL(실제 펌웨어의 PC 빌드)이 Gazebo Harmonic과 공식 연동되고 RC 입력을 UDP 9004로 받으므로, 동일한 제어 코드로 시뮬(BuddyBoxSitl)과 실물(BuddyBox)을 오가며 개발할 수 있다.

## 2026-07-20

- **Q. 빈 씬은 확실히 빠른데 왜 데모 월드는 느린가?**
  → 조건이 달랐다 — 빈 씬은 GPU 렌더링으로 띄웠고 데모 월드 스크립트는 기본이 소프트웨어 렌더링 강제라서, 같은 조건 비교(`start_gazebo.sh gpu` 또는 `LIBGL_ALWAYS_SOFTWARE=1 gz sim shapes.sdf`)로 렌더링 탓인지 월드 탓인지 가려야 한다.

- **Q. shapes에 드론을 얹으니 확실히 느려지는데 왜인가?**
  → 헤드리스 RTF 측정 결과 shapes 단독 1.00 / shapes+드론(1ms 스텝) 0.45 / 데모 경량 월드(4ms 스텝, Betaflight 플러그인 포함) 1.00 — shapes의 기본 물리 스텝(1ms)이 데모 월드(4ms)보다 4배 촘촘해서 느려진 것이고, 실제 데모 월드의 물리는 실시간 100%라서 남은 용의자는 드론 메시(dae) GUI 렌더링이다.

- **Q. 드론 비주얼을 없앤 버전은 부드러운데, 그럼 결론은?**
  → 범인은 드론 dae 메시의 WSLg GUI 렌더링으로 확정 — 물리는 그대로 두고 비주얼만 박스+실린더로 바꾼 `betaloop_iris_simplevis` 모델을 만들어 `light` 월드에 연결했고, 개발 시에는 `start_gazebo.sh gpu light`를 쓰면 된다 (제어·SITL 동작은 원본과 동일).

- **Q. Meteor75 기준으로 만들어진 URDF나 드론 모델이 있나?**
  → 로컬(레포·/opt/buddybox-sitl)과 웹 모두에 기성 Meteor75 URDF/SDF는 없다 — 공개된 것은 3D 프린트용 케이스 모델이나 상용 FPV 시뮬레이터 지원뿐이라, 필요하면 iris 모델의 질량·크기·모터 파라미터를 1S 75mm whoop 사양으로 바꿔 직접 만들어야 한다.

- **Q. Meteor75와 비슷한 형태의 오픈소스로 STEP 파일(그리고 URDF)이 있는 게 있나?**
  → Meteor75 그대로인 STEP+URDF 세트는 없다 — 형태가 가장 비슷한 오픈소스는 vsergeev/3d-parametric-whoop(65/75mm 덕트 프레임, OpenSCAD+STL, CC-BY, STEP은 FreeCAD 변환 필요)이고, CAD+URDF가 다 갖춰진 초소형 쿼드는 Crazyflie 2.1(단 27mm 프롭, 덕트 없음)이 유일하며, 우리 SITL엔 URDF가 아닌 SDF가 쓰이므로 iris SDF를 whoop 사양으로 튜닝하는 게 현실적이다.

- **Q. (parametric-whoop) 그걸로 활용해보자, 다운받아줘 — 75mm 버전도 있나?**
  → `C:\VisionWorkspace\3d-parametric-whoop`에 클론했고 75mm 버전(`stl/75mm_26x26_whoop.stl`, 99.5×99.5×15mm, 36k 삼각형)이 있어서, betaloop_meteor75 모델의 프레임 판·덕트 단순 도형 6개를 이 실제 프레임 STL 비주얼로 교체했다(원본은 model.sdf.bak, 물리·충돌체는 변경 없음, CC-BY 출처 주석 포함).

- **Q. 아까는 창이 떴는데 왜 이제는 안 뜨나?**

- **Q. 다운받은 링크 보여줘 — 가운데가 큐브인데 너무 형편없다?**
  → 링크는 https://github.com/vsergeev/3d-parametric-whoop 이고, 큐브는 다운받은 모델이 아니라 남겨뒀던 파란 박스 캐노피 자리표시자였다 — 레포에 같이 든 진짜 캐노피 STL(betafpv_c03_26x26_canopy.stl, 8.5k 삼각형)로 교체해 프레임·캐노피 모두 실제 형상이 됐고, 이 상태로 `run_all.sh gpu meteor` 전체 체인(SITL 가상 비행 ARM→호버→DISARM)도 완주했다.

- **Q. 지금 시뮬이 Betaflight 기준으로 돌아가는 건가?**
  → 그렇다 — 조종 두뇌는 실기체 FC와 같은 소스를 PC용으로 빌드한 Betaflight SITL(ARM·PID·모드 전부 실제 펌웨어 코드)이고, Gazebo는 물리(질량·추력·공기역학·IMU)만 담당하며, virtual_flight.py는 조종기 역할로 RC 값(UDP 9004)만 보내므로 시뮬에서 검증한 제어 코드를 실물에 그대로 쓸 수 있다.

- **Q. 그러면 지금 움직일 때 뭘로 움직이고 있나?**
  → 조종사는 virtual_flight.py 스크립트다 — BuddyBoxSitl이 가상 조종기로 RC 값을 보내는데 스로틀 채널만 올렸다 내리고(1100→1700→1000µs) Roll/Pitch/Yaw는 중립, ARM은 AUX1=1900이며, 수평 유지는 Betaflight PID가 담당하고 고도는 개루프다 — 이 RC 입력 지점에 나중에 자율 제어/학습 정책을 꽂으면 된다.

- **Q. Gazebo 창이 간헐적으로 안 뜨는 이유는?**
  → 셸 구분 문제(`wsl` 접두어는 PowerShell 전용 — WSL 리눅스 셸 안에서는 빼고 `bash /mnt/c/...`로 실행)와, Windows 쪽 WSLg 표시 클라이언트(msrdc)가 창을 받아놓고 안 그리는 간헐적 버그 두 가지였다 — 후자는 `wsl --shutdown`(리눅스 안에서는 `wsl.exe --shutdown`) 후 재실행이 임시 처방, `wsl --update`가 근본 조치다.

- **Q. 드론이 땅바닥에 안 붙어 있는데(공중부양)?**
  → 충돌 박스(높이 30mm)가 링크 원점 중심에 있어 원점을 지면에서 15mm 띄우는데 새 프레임 메시는 원점 위(+3~+18mm)에 그려져 ~18mm 떠 보였던 것 — 충돌 박스 pose를 z=0.018로 올려 메시 바닥과 맞추니 착지 z=-0.003(프레임 바닥=지면)으로 정확히 앉고, 헤드리스 가상 비행(이륙~착지)도 정상임을 확인했다. 교훈: 비주얼을 교체하면 충돌체와의 정렬(착지 높이)도 함께 검증해야 한다.

- **Q. Meteor75 모델을 한번 직접 만들어볼래?**
  → iris를 스케일다운한 `betaloop_meteor75` 모델(75mm 휠베이스, 45mm 프롭, AUW ~48g)과 전용 월드를 만들어 헤드리스로 이륙~착륙 검증까지 완료했다 — 초소형 기체는 1g 로터 링크가 물리 발산(ODE AABB 크래시)하므로 5g으로 패딩하고, 모터 P게인은 관성에 비례해 축소(0.01→5e-4), LiftDrag area는 실측 역산으로 맞춰야 한다(0.4, 호버 스로틀 ~41%).
## 2026-09-10

- **Q. BuddyBox로 Meteor75 Pro 2가 VRX Pro 피드에서 사람을 추적하며 호버링하게 하려면 뭐가 필요한가?**
  → 기존 `realtime_uvc.py`의 UVC 캡처·RF-DETR 검출·녹화를 `buddybox/vision/`으로 포팅하고, 그 위에 화면 오차(가로 위치→yaw, 박스 높이→pitch, 세로 위치→throttle 보정) PID 컨트롤러와 STANDBY/HOVER/FOLLOW 감독기(`buddybox/follow/`)를 얹어 SafetyLimiter→BuddyBox/SITL/sim으로 보내는 구조로 만들었고, tkinter UI(`examples/person_follow.py`)에서 연결·모드·실시간 튜닝·녹화·CSV 로그를 다룬다 — ARM과 최종 제어권(SH 스위치)은 설계 원칙대로 조종기에 남긴다.

- **Q. UI를 띄우면 몇 초 뒤 추론이 55ms에서 500ms로 느려지는데 왜인가?**
  → UI 창이 배경으로 가면 onnxruntime이 논리 코어 32개 전부에 띄운 스핀 스레드가 선점당해 병렬 구간이 늘어지는 현상이었다 — 창을 최상위로 두면 60ms, 전력 스로틀링 해제는 무효, 우선순위 HIGH는 오히려 악화, ORT 스레드를 코어 절반(16)으로 제한하면 배경에서도 60ms라서 기본값을 `cpu_count//2`(`--threads`)로 고정했다.

- **Q. 고도 센서가 없는데 호버링 유지는 어떻게 하나?**
  → 절대 고도는 알 수 없으므로 `hover_throttle` 트림(조종기로 호버시킬 때의 스로틀 위치)을 기본으로 두고, 사람 박스의 세로 위치가 목표선에서 벗어난 만큼만 ±0.12 범위에서 스로틀을 보정한다(고도 보조) — 사람이 없거나 LOST면 트림으로 복귀하고, 필요 없으면 UI에서 끌 수 있다.

- **Q. HOVER 에서 기체가 너무 세게 위로 올라가는데(FOLLOW 도 마찬가지) 스테디하게 유지하는 방법이 있나?**
  → 고도 센서가 없어 HOVER 는 고정 트림을 보내는 개루프인데 기본 트림 -0.2(≈40%)가 Gazebo 모델 기준이라 실물 1S 훕(호버 30~35%)에는 너무 높았고, FOLLOW 는 ±0.12 보정으로 그 오차를 못 이긴 채 사람이 화면 밖으로 빠지면 LOST→잘못된 트림 복귀→더 상승하는 악순환이었다 — 기본 트림을 -0.35 로 낮추고, 추적 중 호버 트림을 자동 학습(위 +0.10/아래 -0.30)해 LOST 때도 학습값으로 호버하며 3초 넘게 잃으면 서서히 하강하게 했고, 고도 기준을 박스 중심에서 머리로 바꾸고(다리 잘림 오판 방지) 스로틀 전용 슬루(0.6/s)와 Kd 를 넣었다. 그래도 완전한 고도 유지는 불가능하므로 조종기 Thr 을 EdgeTX `+=` 로 두고 PC 는 보정만 더하는 offset 모드, FC 에 baro 가 있으면 Betaflight ALT_HOLD 가 대안이다.

- **Q. PID 도 다시 세팅해야 할 것 같고, 전체적으로 디버깅할 수 있게 영상 프레임도 분석하기 좋은 구조로 만들 수 있나?**
  → STANDBY 를 벗어나면 세션 폴더(`recordings/session_*`)에 원본 영상 raw.mp4 + 제어 스텝별 frames.jsonl(검출 박스·트랙·오차·PID 출력·µs·트림) + events.jsonl + 설정/메타가 자동 기록되고, `tools/session_report.py`(요약 report.md, 프레임 격자 sheet.png, 시계열 plot.png, CSV)와 `tools/session_replay.py`(같은 검출 입력에 다른 PID 설정을 개루프로 다시 돌려 비교)로 비행 없이도 분석·재튜닝할 수 있다.
